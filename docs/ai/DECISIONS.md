## ADR-001: 为什么选择 Zustand 而不是 Redux

**日期**: 2026-02-15  
**状态**: ✅ 已采纳  
**决策者**: 核心团队

### 决策

使用 Zustand 作为全局状态管理方案，而不是 Redux。

### 背景

项目需要一个全局状态管理方案来管理：
- 应用实例状态
- 窗口位置和尺寸
- 书签和便签数据
- 用户设置和主题

### 理由

1. **API 简洁**：Zustand 的 API 比 Redux 简单 10 倍
2. **无 Provider 嵌套**：不需要在根组件包裹 Provider
3. **TypeScript 支持更好**：类型推导更准确
4. **包体积更小**：Zustand 仅 1KB，Redux 需要 10KB+
5. **学习曲线平缓**：新成员 5 分钟即可上手

### 后果

**正面影响**：
- 代码量减少 50%
- 开发效率提升
- 类型安全性更好

**负面影响**：
- 缺少 Redux DevTools 的时间旅行功能
- 需要手动管理状态切片
- 社区生态不如 Redux 丰富

### 替代方案

**方案 A: Redux Toolkit**
- 优点：成熟生态，DevTools 强大
- 缺点：样板代码多，学习曲线陡峭
- 为什么不选：过度工程，不符合"简化"哲学

**方案 B: Jotai**
- 优点：原子化状态，更细粒度
- 缺点：概念复杂，不适合大型状态
- 为什么不选：过于分散，不适合窗口管理

**方案 C: MobX**
- 优点：响应式，自动追踪依赖
- 缺点：魔法太多，调试困难
- 为什么不选：违背"显式优于隐式"原则

## ADR-002: 为什么不使用路由

**日期**: 2026-02-10  
**状态**: ✅ 已采纳  
**决策者**: 核心团队

### 决策

不使用 React Router，窗口即应用实例，状态驱动 UI。

### 背景

传统 Web 应用使用 URL 路由来管理页面跳转，但 KYO 是一个桌面 OS 模拟器。

### 理由

1. **桌面 OS 不需要 URL**：真实的 macOS/Windows 没有地址栏
2. **窗口状态更直观**：打开/关闭窗口比 URL 跳转更自然
3. **避免路由复杂度**：不需要处理路由守卫、嵌套路由、动态路由
4. **多实例支持**：同一个应用可以打开多个窗口
5. **状态持久化更简单**：直接保存窗口状态到 Store

### 后果

**正面影响**：
- 代码更简洁
- 多实例支持天然
- 状态管理更直观

**负面影响**：
- 无法通过 URL 分享应用状态
- 浏览器后退键无效
- SEO 不友好（但 KYO 不需要 SEO）

### 替代方案

**方案 A: React Router**
- 优点：成熟方案，URL 可分享
- 缺点：不符合桌面 OS 的交互模式
- 为什么不选：过度工程，违背设计理念

**方案 B: URL 状态 + 窗口管理**
- 优点：兼顾 URL 和窗口
- 缺点：复杂度翻倍，状态同步困难
- 为什么不选：增加不必要的复杂度

## ADR-003: 为什么使用 IndexedDB 而不是 LocalStorage

**日期**: 2026-02-08  
**状态**: ✅ 已采纳  
**决策者**: 核心团队

### 决策

使用 IndexedDB 作为虚拟文件系统的后端存储。

### 背景

需要在浏览器中存储大量数据（书签、便签、文件），LocalStorage 有 5MB 限制。

### 理由

1. **容量更大**：IndexedDB 可存储 GB 级数据
2. **支持 Blob**：可以存储图片、音频等二进制数据
3. **异步 API**：不阻塞主线程
4. **事务支持**：保证数据一致性
5. **索引查询**：支持复杂查询

### 后果

**正面影响**：
- 可以存储大量数据
- 性能更好
- 支持更多数据类型

**负面影响**：
- API 复杂，需要封装
- 浏览器兼容性需要处理
- 调试困难

### 替代方案

**方案 A: LocalStorage**
- 优点：API 简单，同步操作
- 缺点：容量限制 5MB，只能存字符串
- 为什么不选：容量不足，无法存储文件

**方案 B: WebSQL**
- 优点：SQL 查询，熟悉的 API
- 缺点：已废弃，浏览器不再支持
- 为什么不选：技术已死

**方案 C: 云存储（Supabase）**
- 优点：无容量限制，多设备同步
- 缺点：需要网络，离线不可用
- 为什么不选：违背"数据主权"理念（但会作为可选功能）

## ADR-004: 为什么使用 Vercel AI SDK

**日期**: 2026-02-05  
**状态**: ✅ 已采纳  
**决策者**: 核心团队

### 决策

使用 Vercel AI SDK 作为 AI 集成的统一接口。

### 背景

需要集成多个 AI 模型（OpenAI、Anthropic、Google），需要一个统一的接口。

### 理由

1. **统一接口**：一套 API 支持多个模型
2. **流式响应**：原生支持 SSE
3. **React Hooks**：`useChat` 开箱即用
4. **类型安全**：完整的 TypeScript 支持
5. **Vercel 生态**：与 Vercel 部署无缝集成

### 后果

**正面影响**：
- 开发效率高
- 切换模型简单
- 流式响应体验好

**负面影响**：
- 绑定 Vercel 生态
- 自定义能力有限

### 替代方案

**方案 A: 直接调用 OpenAI API**
- 优点：完全控制，无中间层
- 缺点：需要自己处理流式响应、错误处理
- 为什么不选：重复造轮子

**方案 B: LangChain**
- 优点：功能强大，支持复杂流程
- 缺点：过于复杂，学习曲线陡峭
- 为什么不选：过度工程，不符合"简化"哲学

## ADR-005: 为什么使用 Dify 而不是自建 Chatflow

**日期**: 2026-02-03  
**状态**: ✅ 已采纳  
**决策者**: 核心团队

### 决策

使用 Dify 作为聊天流管理平台，而不是自己实现。

### 背景

需要实现复杂的对话流程，包括上下文记忆、工具调用、知识库检索。

### 理由

1. **可视化编排**：无需写代码即可配置对话流
2. **上下文管理**：自动处理多轮对话
3. **工具调用**：支持 Function Calling
4. **知识库集成**：支持文档检索
5. **快速迭代**：修改流程无需重新部署

### 后果

**正面影响**：
- 开发效率极高
- 非技术人员也能配置
- 功能强大

**负面影响**：
- 依赖第三方服务
- 自定义能力有限
- 需要额外成本

### 替代方案

**方案 A: 自建 Chatflow**
- 优点：完全控制，无依赖
- 缺点：开发成本高，功能有限
- 为什么不选：重复造轮子，不符合"实用主义"

**方案 B: LangChain**
- 优点：开源，功能强大
- 缺点：需要自己部署和维护
- 为什么不选：维护成本高

## ADR-006: 为什么使用 Bun 而不是 npm/pnpm

**日期**: 2026-01-28  
**状态**: ✅ 已采纳  
**决策者**: 核心团队

### 决策

使用 Bun 作为包管理器和运行时。

### 背景

需要一个快速的包管理器和运行时来提升开发体验。

### 理由

1. **速度极快**：安装速度比 npm 快 10 倍
2. **内置运行时**：可以直接运行 TypeScript
3. **兼容 npm**：可以使用所有 npm 包
4. **内置工具**：自带测试、打包、转译
5. **现代化**：原生支持 ESM、TypeScript

### 后果

**正面影响**：
- 开发效率提升
- CI/CD 时间缩短
- 开发体验更好

**负面影响**：
- 生态不如 npm 成熟
- 部分包可能不兼容
- 团队需要学习新工具

### 替代方案

**方案 A: npm**
- 优点：最成熟，兼容性最好
- 缺点：速度慢，功能有限
- 为什么不选：速度太慢，影响开发体验

**方案 B: pnpm**
- 优点：速度快，节省磁盘空间
- 缺点：兼容性问题多
- 为什么不选：Bun 更快，功能更多

**方案 C: Yarn**
- 优点：速度快，功能丰富
- 缺点：不如 Bun 快
- 为什么不选：Bun 是未来

## ADR-007: 为什么使用 Tauri 而不是 Electron

**日期**: 2026-01-25  
**状态**: ✅ 已采纳  
**决策者**: 核心团队

### 决策

使用 Tauri 2.0 作为桌面应用框架（可选）。

### 背景

需要提供桌面应用版本，让用户可以离线使用。

### 理由

1. **体积更小**：Tauri 应用仅 3MB，Electron 需要 100MB+
2. **性能更好**：使用系统 WebView，内存占用更少
3. **安全性更高**：Rust 编写，内存安全
4. **启动更快**：不需要启动 Chromium
5. **现代化**：支持最新的 Web 标准

### 后果

**正面影响**：
- 应用体积小
- 性能好
- 安全性高

**负面影响**：
- 生态不如 Electron 成熟
- 调试困难
- 需要学习 Rust（可选）

### 替代方案

**方案 A: Electron**
- 优点：生态成熟，兼容性好
- 缺点：体积大，性能差
- 为什么不选：违背"简化"哲学

**方案 B: NW.js**
- 优点：类似 Electron，但更轻量
- 缺点：生态不如 Electron
- 为什么不选：不如 Tauri 轻量
