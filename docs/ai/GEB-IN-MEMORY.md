# GEB 协议在 Memory 系统中的体现

> 记忆也是代码的一种形式，必须遵循 GEB 分形文档系统协议

---

## 核心理念

**GEB 协议的本质**：代码是机器相，文档是语义相，两相必须同构。

**应用到记忆系统**：
- **记忆的机器相** = 实际发生的事件、决策、问题（历史事实）
- **记忆的语义相** = 记忆文档的描述（文字记录）
- **两相同构** = 记忆文档必须准确反映历史事实，不能虚构或遗漏

---

## 记忆的三层分形结构

### L1 - 记忆宪法（MEMORY.md）

**位置**: `.claude/memory/MEMORY.md`

**职责**:
- 记忆分类体系（按主题组织）
- 记忆更新协议（何时更新、如何更新）
- 记忆检索规则（如何快速找到相关记忆）
- 记忆归档策略（何时归档、如何归档）
- 记忆统计信息（总数、状态、最后更新）

**L1 头部**:
```markdown
/**
 * [INPUT]: 来源于所有 session 的经验积累
 * [OUTPUT]: 对外提供记忆索引、分类体系、检索规则
 * [POS]: memory/ 的顶层索引，统领所有主题记忆
 * [PROTOCOL]: 变更时更新此头部，新增主题记忆时必须更新索引
 */
```

### L2 - 主题记忆（如 dify.md）

**位置**: `.claude/memory/{topic}.md`

**职责**:
- 特定主题的已知问题
- 最佳实践
- 避免的坑
- 性能优化
- 调试技巧

**L2 头部**:
```markdown
/**
 * [INPUT]: 来源于 {日期范围} 的开发 session，{相关文件} 的实际问题
 * [OUTPUT]: 对外提供 {主题} 的已知问题、最佳实践、避免的坑
 * [POS]: memory/ 的 {主题} 记忆，与 {其他主题}.md 并列
 * [PROTOCOL]: 变更时更新此头部，然后检查 MEMORY.md
 */
```

**L2 元数据**:
```markdown
> **记忆状态**: ✅ 稳定 / 🚧 进行中 / ⚠️ 待验证
> **最后更新**: YYYY-MM-DD
> **记忆来源**: N 个 session，M+ 次调试
> **影响范围**: {相关文件}
```

### L3 - 每条记忆的元数据

**位置**: 每条具体记忆的头部

**职责**:
- 记录何时发生
- 记录来源（哪个 session、哪个文件）
- 记录状态（已解决/进行中/待验证）
- 记录影响范围
- 记录关联记忆

**L3 元数据**:
```markdown
**[META]**
- **日期**: YYYY-MM-DD
- **来源**: Session #{session-id}, {file}:{line}
- **状态**: ✅ 已解决 / 🚧 进行中 / ⚠️ 待验证
- **影响**: {影响的功能}
- **关联**: {相关记忆的链接}
```

## 记忆的强制回环工作流

### 正向流（事件→记忆）

```
事件发生（Bug、决策、优化）
    ↓
STEP 1: 记录到主题记忆（L2）
    ├─ 添加 [META] 元数据
    ├─ 记录现象、原因、解决方案
    ├─ 添加验证状态
    └─ 记录教训
    ↓
STEP 2: 更新记忆索引（L1）
    ├─ 更新记忆统计
    ├─ 更新最后更新时间
    └─ 添加新主题（如果需要）
    ↓
STEP 3: 关联相关记忆（L3）
    └─ 在 [META] 中添加关联链接
    ↓
记忆完成
```

### 逆向流（查询记忆）

```
遇到问题
    ↓
STEP 1: 查询记忆索引（L1）
    └─ 找到相关主题
    ↓
STEP 2: 读取主题记忆（L2）
    └─ 查找相似问题
    ↓
STEP 3: 检查记忆元数据（L3）
    ├─ 确认状态（已解决？）
    ├─ 查看来源（哪个文件？）
    └─ 跟踪关联（相关问题？）
    ↓
应用解决方案
```

## 记忆的禁止行为

### 死罪（立即中止）

- **FATAL-001 虚构记忆**: 记录未实际发生的事件
- **FATAL-002 遗漏关键信息**: 不记录来源、日期、状态
- **FATAL-003 不更新索引**: 添加主题记忆但不更新 MEMORY.md
- **FATAL-004 记忆孤岛**: 不关联相关记忆，导致知识碎片化

### 重罪（警告后修复）

- **SEVERE-001 记忆过时**: 问题已解决但状态未更新
- **SEVERE-002 缺少验证**: 解决方案未经验证就记录
- **SEVERE-003 缺少教训**: 只记录问题和解决方案，不总结教训
- **SEVERE-004 缺少元数据**: 记忆没有 [META] 标签

## 记忆模板

### 已知问题模板

```markdown
### 问题 {N}: {问题标题}

**[META]**
- **日期**: YYYY-MM-DD
- **来源**: Session #{session-id}, {file}:{line}
- **状态**: ✅ 已解决 / 🚧 进行中 / ⚠️ 待验证
- **影响**: {影响的功能}
- **关联**: {相关问题链接}

**现象**: 
{具体表现}

**原因**: 
{根本原因分析}

**解决**: 
```code
{解决方案代码}
```

**验证**: 
- ✅ {验证项 1}
- ✅ {验证项 2}

**教训**: 
- {从这个问题学到了什么}
- {如何避免类似问题}
```

### 最佳实践模板

```markdown
### {实践编号}. {实践标题}

**[META]**
- **来源**: {问题编号} 的解决方案
- **验证**: ✅ {验证结果}

```code
{最佳实践代码}
```

**说明**:
{为什么这是最佳实践}
```

### 避免的坑模板

```markdown
### {坑编号}. {坑标题}

**[META]**
- **来源**: {问题编号}
- **严重程度**: 高/中/低
- **影响**: {影响范围}

❌ **错误**:
```code
{错误做法}
```

✅ **正确**:
```code
{正确做法}
```

**说明**:
{为什么会踩坑，如何避免}
```

## 记忆统计

每个主题记忆（L2）应该包含统计信息：

```markdown
## 记忆统计

- **总问题数**: {N}
- **已解决**: {N}
- **进行中**: {N}
- **待验证**: {N}
- **最佳实践**: {N}
- **避免的坑**: {N}
- **性能优化**: {N}
```

记忆索引（L1）应该包含全局统计：

```markdown
## 全局统计

- **总主题数**: {N}
- **总问题数**: {N}
- **总最佳实践**: {N}
- **总避免的坑**: {N}
- **最活跃主题**: {主题名}
- **最后更新**: YYYY-MM-DD
```

## 记忆归档策略

### 触发条件

- 主题记忆超过 1000 行
- 问题数超过 50 个
- 时间跨度超过 6 个月

### 归档流程

```
1. 创建归档文件
   {topic}-archive-YYYY.md

2. 移动旧记忆
   保留最近 6 个月的记忆
   移动更早的记忆到归档文件

3. 更新索引
   在 MEMORY.md 中添加归档链接

4. 保持统计
   归档文件也要有统计信息
```

## 示例：符合 GEB 协议的记忆文档

参考 `.claude/memory/dify.md`，它完整体现了 GEB 协议：

1. **L2 头部** - 明确 INPUT/OUTPUT/POS
2. **L2 元数据** - 记忆状态、来源、影响范围
3. **L3 元数据** - 每条记忆的 [META] 标签
4. **验证状态** - 每个解决方案都有验证
5. **教训总结** - 每个问题都有教训
6. **记忆统计** - 清晰的统计信息
7. **更新日志** - 完整的变更历史

## 记忆与代码的同构

### 代码变更 → 记忆更新

```
修复 Bug
    ↓
记录到主题记忆
    ├─ 问题现象
    ├─ 根本原因
    ├─ 解决方案
    └─ 验证结果
    ↓
更新记忆索引
```

### 记忆查询 → 代码修改

```
遇到问题
    ↓
查询记忆
    ├─ 找到相似问题
    ├─ 查看解决方案
    └─ 检查验证状态
    ↓
应用解决方案
    ↓
验证是否有效
    ↓
更新记忆状态
```

## 终极真理

> 记忆不是静态的文档，是动态的知识系统。  
> 记忆不是个人的笔记，是团队的资产。  
> 记忆不是可选的附加，是必需的基础设施。  
> 
> 没有记忆的 AI Agent，每次都从零开始。  
> 有记忆的 AI Agent，越用越聪明。  
> 
> 记忆即认知，遗忘即退化。
